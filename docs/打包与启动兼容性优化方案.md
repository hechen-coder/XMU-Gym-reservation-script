## 1. 目标与约束

本轮优化保留现有 Python 3.8 构建路线，通过运行层修复兼容性问题，并完善发布流程。升级 Python 不作为本方案的前置条件。

用户已明确补充：缺少 WebView2 时，当前程序会自动打开默认浏览器，访问本地 `http://127.0.0.1:端口`。这是需要改进的现状，不是期望保留的默认体验。目标是让预约界面在应用窗口内正常打开；缺失运行时时先提供检测和安装修复，不能直接跳到默认浏览器，更不能要求普通用户手动输入本地地址。

浏览器访问仅保留为用户主动选择的应急方式。Release 计划同时提供便携 ZIP 与安装版 Setup.exe；ZIP 是完整应用目录的压缩包，包内的主程序 EXE 不等于独立单文件版，也不等于安装器。两种发布形式使用同一应用构建，均优先使用应用内界面。

目标包括：

- 中文电脑名下，本地 HTTP 服务正常启动。
- 双击后优先在应用内显示界面；不可用时显示可操作的修复窗口或明确的启动失败提示。
- 应用内页面及用户主动选择的应急浏览器页面，只在本地服务确认就绪后打开。
- WebView2 不可用时，提供安装或修复入口，修复后重新进入应用；不自动打开默认浏览器。
- 构建结果可复现，配置、授权和日志不混入公开发布包。
- 安装版、便携版、快捷方式和 CLI 的行为一致且可解释。

本轮已修改运行与打包代码；下文是完整设计，其中实际实现和未验收边界以上方实施状态及发布指南为准。

## 3. 问题分类与处理方向

| 现象 | 应如何理解 | 优化方向 |
| --- | --- | --- |
| 有进程，但无可见界面 | 可能停在导入、GUI 初始化、后台等待或托盘隐藏阶段 | 早期日志、启动阶段标记、异常提示、可恢复的后台控制入口 |
| 窗口或浏览器显示拒绝连接 | 本地服务可能未启动、已退出，或访问了错误端口 | 修复绑定、就绪握手、实际端口传递、错误分类 |
| 缺少 WebView2 后打开本地网页 | 当前自动回退行为，与用户期望的应用内体验不符 | 改为原生修复窗口；优先安装或修复 Runtime，浏览器仅由用户主动选择 |
| Runtime 存在但窗口空白 | 可能是异步初始化、页面加载或应用侧 DLL 问题 | 记录底层异常，分开检查服务健康与窗口健康 |

## 4. 保留 Python 3.8 的运行层修复

### 4.1 中文主机名异常的触发链

当前解释器的标准库在 `HTTPServer.server_bind()` 中执行：

```text
ThreadingHTTPServer 构造
  → HTTPServer.server_bind()
  → socket.getfqdn(host)
  → 主机名反向解析
  → 部分 Windows 编码环境下抛出 UnicodeDecodeError
```

`UnicodeDecodeError` 不属于 `OSError`，因此当前捕获端口异常的分支无法处理它。服务线程结束后，主线程仍可能继续打开窗口或浏览器。

与此类 Windows ANSI/UTF-8 主机名解码问题对应的官方记录是 [CPython bpo-26227 / GitHub #70415](https://github.com/python/cpython/issues/70415)，其中列有 Python 3.9 的回移修复。不能直接沿用“bpo-36270、只有 3.10 才修复”的说法。

### 4.2 首选方法：专用本地 HTTPServer 子类

本地控制台不需要计算本机 FQDN。应只调整本项目服务器的绑定行为，继续复用标准库的线程处理与请求处理器。

以下为可供后续实施参考的 Python 3.8 兼容示例，当前未写入运行代码：

```python
import socketserver
from http.server import ThreadingHTTPServer


class LoopbackHTTPServer(ThreadingHTTPServer):
    """仅用于 IPv4 回环服务，绑定时不执行主机名反向解析。"""

    def server_bind(self):
        socketserver.TCPServer.server_bind(self)
        host, port = self.server_address[:2]
        self.server_name = host
        self.server_port = port
```

使用约束：

1. 桌面和浏览器控制台统一绑定明确的 `127.0.0.1`，避免通过 `localhost` 解析选择地址。
2. 主 Web 服务与独立 CAS 服务都应复用此实现，避免遗漏第二个入口。
3. 示例只覆盖 IPv4 回环，不声称同时支持 IPv6；若保留 `::1`，需单独定义并验证地址族。
4. 不全局覆盖 `socket.getfqdn`，不影响学校 API、SMTP 或其他第三方库的网络行为。
5. 不修改用户电脑名、系统编码、hosts 文件或安装目录中的 Python 标准库。
6. `PYTHONUTF8`、控制台 UTF-8、文件读写编码不能作为此底层解码问题的可靠修复。

仅捕获 `UnicodeDecodeError` 后继续打开界面也不够，因为构造失败时并不存在可用服务器。应先消除不必要的解析，再把其他启动异常准确传回主线程。

### 4.3 Python 版本保留与依赖固定

保留当前解释器版本，不代表每次构建都从网络安装最新依赖。建议建立经验证的 Python 3.8 Windows x64 构建环境：

- 固定解释器完整版本、位数、PyInstaller、hooks、pywebview、pythonnet、ddddocr、ONNX Runtime、PyArmor 和其传递依赖。
- 基于干净环境生成发布依赖清单，不直接把整个 Anaconda 环境的包全部冻结为项目依赖。
- 为实际用到的依赖保留可验证的 wheel 集合和哈希，避免重建时重新解析出不同版本。
- 区分运行依赖、构建依赖、测试依赖；不把 pytest 作为用户运行必需项。
- 记录本方案修复的是已识别的启动路径，不把它表述为解决所有 Python 3.8 兼容问题。

不在实施前承诺任意新版依赖支持 Python 3.8；固定版本必须以本项目实测为准。

## 5. 用启动握手替代固定等待

### 5.1 推荐结构

把“构造服务器”和“阻塞运行服务器”拆分：

```text
Bootstrap：初始化日志、目录、异常钩子
  → 单实例协调
  → 创建服务器对象并获取实际端口
  → 启动服务线程，启动结果通过 Event / Queue 回传
  → 请求轻量健康接口，核对本次实例
  → 检查并准备 WebView2；缺失时显示原生修复窗口
  → 应用内打开；只有用户主动选择时才使用应急浏览器
  → 保持可见的运行控制入口
  → 停止业务任务与服务器，释放资源
```

建议新增服务器工厂和运行控制对象，保留 `run_server()` 作为 CLI 兼容包装。控制对象持有服务器、线程、停止事件、实际 URL 和启动错误，避免各处重复推测状态。

### 5.2 健康接口要求

建议新增 `/healthz`：

- 不读取登录凭据、不查询学校接口、不初始化 OCR、不计算硬件指纹。
- 返回固定应用标识、协议版本、本次启动随机标识和服务就绪状态。
- 主线程使用内存中的预期随机标识校验返回值，识别当前实例。
- 随机标识仅作就绪关联，不作为授权凭据，也不赋予业务操作权限。
- 绑定回环地址；保留现有来源检查及业务权限控制。
- 使用 `Cache-Control: no-store`，不向日志输出随机标识或敏感配置。

不得以 `/api/status` 或首页作为启动探针：当前这些路由涉及业务查询，不能区分学校接口慢与本地服务器没启动。

建议初始总等待上限为 15 秒，每次探针设短超时，使用单调时钟计算截止时间；数值需根据冷启动实测调整。线程异常或提前退出应立即失败，不必等满超时。探针连接回环时显式绕过代理，不全局关闭用户网络代理。

### 5.3 就绪的定义

端口绑定成功不等于 HTTP 可响应；HTTP 可响应不等于业务已登录。服务应先提供无需外部网络的健康与初始页面，再异步启动登录监控、OCR 预热等可选工作。

启动后还需监测服务线程的意外退出；若窗口仍在，应显示服务中断提示，不能长期保留失去后端的页面。

### 5.4 端口和错误分类

| 情况 | 推荐行为 |
| --- | --- |
| 桌面默认端口被其他程序占用 | 从候选端口重新绑定或直接使用系统分配端口，使用实际地址打开界面 |
| 用户通过 CLI 显式指定端口，绑定失败 | 明确报告失败并返回非零退出码，不静默改变用户配置 |
| 权限不足或地址不可用 | 单独提示权限或地址问题，保留原始错误码 |
| 已有同一应用实例 | 经过实例识别后唤起已有实例，不以端口占用代替身份确认 |
| 任意未预期启动异常 | 写入堆栈，向启动器返回失败，并提供诊断入口 |

不要先探测空闲再释放端口，随后重新绑定，这会产生竞争窗口。应保留成功绑定的服务器套接字，并通过 `server_address` 获取实际端口。

所有窗口、浏览器、托盘菜单、状态展示和第二实例唤起都使用同一个实际 URL。当前 CLI `web --port ...` 的自动打开地址也需随参数变化。

## 6. 应用内界面优先与 WebView2 修复策略

### 6.1 明确产品行为

默认采用“应用内界面优先、失败先修复”的策略。预约页面仍由本机 HTTP 服务提供，但通过内嵌 WebView2 显示在应用窗口中，本地地址无需普通用户输入。WebView2 初始化失败后不得自动调用 `webbrowser.open()`。

缺少渲染引擎时不能依靠 WebView2 绘制修复界面。应使用不依赖 WebView2 的原生窗口或对话框，提供安装修复、重试和退出入口；应急浏览器入口放在次要位置，由用户主动点击。

建议保留或逐步补齐以下模式：

| 模式 | 预期行为 |
| --- | --- |
| 默认应用模式 | 应用内打开；缺少 Runtime 时显示修复窗口，修复后重试或重新启动应用 |
| 明确选择应急浏览器模式 | 用户主动点击应急入口或显式执行 CLI `web`，服务就绪后打开浏览器 |
| 手动复制本地地址 | 仅作为高级排查手段，不出现在普通用户首次使用的必经流程 |

这些是行为设计，具体命令名需与现有 `gui`、`desktop`、`web` 参数兼容，不在未实施前宣称新增参数已经可用。

推荐修复提示：

> 当前无法打开应用内界面。检测到 WebView2 Runtime 缺失或不可用，请安装或修复后重试。
>
> 【安装／修复窗口组件】 【重试】 【退出】
>
> 如暂时无法修复，可主动选择“临时使用浏览器”。

若只知道初始化失败，提示中不得直接断言“未安装 Runtime”。日志应区分未检测到、DLL 加载失败、Runtime 初始化失败和页面加载失败。

### 6.2 Runtime 检测与安装

项目收集的 `Microsoft.Web.WebView2.*.dll` 和 `WebView2Loader.dll` 属于应用侧组件，不等于完整浏览器 Runtime。正式 WebView2 应用也不能把 Edge Stable 当成 Runtime 的替代品。[微软官方分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

建议的检测流程：

1. 检查应用侧 DLL 与进程架构是否匹配。
2. 根据官方方法检查 Runtime，包括用户级、机器级注册信息及适用的注册表视图；或使用官方 Loader 版本查询接口。
3. 如使用 Loader 查询，注意它可能识别 Edge 预览通道；生产模式与 pywebview 实际检测结果需一致。
4. 真正创建 WebView2 环境后，再确认初始化结果；预检通过不代表一定可用。
5. 缺失时进入原生修复流程；用户确认后安装或修复 Runtime，成功后重新检测并尝试应用内打开。
6. 用户取消、安装失败或需要联网但网络不可用时，保留修复窗口并提供重试、退出和主动应急入口，不直接打开浏览器。

安装版 Setup 在安装过程中完成 Runtime 检测，需要时使用附带的微软官方 Evergreen Bootstrapper；便携 ZIP 首次启动执行同类预检，缺失时由原生修复窗口调用包内引导安装器。两者均仅在缺失或修复时联网下载，已有 Runtime 时跳过。

默认 ZIP 和 Setup 均为轻量包，只附带约 2 MB 的 Bootstrapper。它减少发布包体积，但不减少缺失 Runtime 时需要下载的完整组件数据量。首次补装需要能访问微软服务；失败时提供明确重试或退出入口，不自动跳浏览器。执行前验证微软来源和签名，安装后再次检测。

安装用户级 Runtime 不等于免安装或零系统变更：便携应用本体无需安装，但首次缺失组件时仍需用户确认安装系统组件，权限限制或组织策略也可能阻止安装。说明文档必须清楚表达这一点。安装完成后优先受控重启应用，再次探测 Runtime；不要在同一进程中假定先前失败的 CLR / pywebview 状态可以直接复用。重试次数有限，避免安装与重启循环。

若以后要求“便携 ZIP 连 Runtime 也无需安装，离线解压即可在应用内使用”，可将完整 Fixed Version Runtime 随包分发，并通过明确路径加载。它不要求注册为 Evergreen Runtime，但体积更大，需自行维护更新，并验证适用系统的访问权限。这是另一条产品路线，不等于把几个 Loader DLL 放进 ZIP。当前采用“内置轻量 Bootstrapper、缺失时联网安装”的方案；完整离线安装器可单独提供，不纳入默认 ZIP 或 Setup。不要通过手工补注册表、扫描任意 Edge 目录或复制他人机器的几个文件来伪装 Runtime 已安装。

### 6.3 异步失败与页面超时

外层 `try/except webview.start()` 只能覆盖部分异常。本机 pywebview 的 WebView2 初始化失败还可能发生在异步回调中，仅写日志后返回。

后续实施应：

- 明确指定现代 `edgechromium` 渲染器，避免无意退回旧 MSHTML；该选择受当前固定 pywebview 版本验证。[pywebview 渲染器文档](https://pywebview.flowrl.com/guide/web_engine.html)
- 分开记录窗口显示、WebView2 初始化、导航成功及前端就绪状态。
- 不把 `shown` 事件当作页面已经正常加载。
- 必要时使用只读前端就绪回调；不要为此扩大通用 JS 桥接权限。
- 超时后重新检查 HTTP 健康；服务失败时报告服务问题，GUI 失败时进入修复流程，不自动切换浏览器。
- 通过统一状态锁保证失败处理只执行一次，关闭失败窗口并清理其托盘；只有用户主动选择应急模式时才打开一次浏览器。
- UI 操作调度到所属消息循环线程，不能从 watchdog 线程直接操作 WinForms 控件。

### 6.4 原生修复窗口与应急模式的进程管理

原生修复窗口和用户主动选择的应急浏览器模式，必须有独立于 WebView2 的运行控制入口，因为现有桌面托盘依赖 WinForms / pythonnet，可能与 GUI 一同不可用。

建议用轻量 Win32 控制窗口提供“安装或修复、重试打开应用、查看日志、退出程序”，并将“临时使用浏览器”放在次要位置；兜底错误提示可用 Win32 MessageBox，不额外要求 Tk 或另一套大型 GUI 库。应急浏览器启用后，可提供托盘或控制窗口管理服务。

- 关闭浏览器标签页不自动终止服务或已开启的预约任务。
- 没有启动任务时，不显示“抢票正在运行”等误导状态。
- 不以长时间无人访问作为退出依据，防止过夜任务被中断。
- 未经用户主动选择，不启动默认浏览器；用户明确使用应急方式后，才在浏览器调用失败时提供复制地址或重试。
- 用户明确退出后才进入停止流程；后台服务意外死亡时不能继续无意义地无限等待。
- 如果控制入口也无法创建，应给出明确错误并退出，不能只留下隐藏进程。

## 7. 无窗口问题的诊断与异常反馈

### 7.1 将启动日志提前

启动器当前在模块顶层执行 `from main import main as cli_main`。应在导入这类业务模块之前建立最小启动日志和异常处理，再延迟导入实际需要的 CLI 或桌面模块。

建议阶段标记：

```text
BOOTSTRAP → PATHS_READY → IMPORTS_READY → INSTANCE_READY
          → SERVER_BOUND → HTTP_READY
          → RUNTIME_CHECK → REPAIR_REQUIRED / GUI_READY
          → RUNNING → STOPPED
```

用户主动启用应急方式时，另记录 `BROWSER_READY`；不得把它记作默认应用内界面验收成功。

每条启动记录包含时间、耗时、发布版本、Python 版本、架构、启动模式、实际端口和错误分类。完整堆栈写入文件，用户提示只展示简短原因、错误编号和日志位置。

同时接入 `sys.excepthook`、Python 3.8 的 `threading.excepthook`，以及明确的服务线程异常回传。不能把关键线程错误仅交给 `sys.stderr`，因为无控制台模式下输出可能不可见。[PyInstaller 无控制台注意事项](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html)

若失败发生在 PyInstaller bootloader、Python DLL 或运行时 hook 初始化之前，应用层异常钩子无法覆盖；此时使用诊断构建和干净机器测试继续定位，不承诺所有无窗口故障都能由 Python 日志捕获。

### 7.2 日志与诊断包

- 使用轮转日志，分别记录启动诊断和业务运行，防止长期挂机耗尽磁盘。
- 程序目录不可写时回退到用户可写目录，不静默丢失全部日志。
- 错误提示避免依赖已经失败的 .NET / WebView2 组件。
- 诊断包只包含脱敏日志、版本清单、启动阶段和必要环境信息。
- 不导出 Cookie、PHPSESSID、密码、通知密钥、授权文件或完整硬件指纹。
- 机器名、用户名和绝对路径可能包含个人信息；导出前做脱敏。

## 8. 单实例、托盘与退出流程

现有命名互斥体可保留，但需要补齐行为与 Win32 调用声明。

- 明确“一位 Windows 用户一个控制中心”的范围；若改用 Local 命名空间，需验证会话及版本共存策略。
- 为 `CreateMutexW`、`CloseHandle` 等设置正确的参数和句柄返回类型，避免 64 位句柄被默认整数类型截断。
- 检查创建失败；发现已有实例时关闭本次新获取的句柄。
- 当前创建参数未请求互斥体所有权，清理应关闭句柄，不能无条件调用释放所有权的 API。
- 通过受限本地 IPC 传递“显示窗口／打开浏览器”的请求，不只依赖固定窗口标题。
- 第二次启动可能遇到首实例尚未就绪，应有短暂等待和准确反馈。
- 桌面、浏览器和安装快捷方式都通过同一协调入口；独立 CLI 命令明确是否属于同一个控制中心。
- 托盘成功创建后才允许隐藏窗口；失败时保留可见窗口或控制入口。

推荐退出顺序：停止接收新任务 → 取消或收束运行任务 → 停止心跳与监控 → 关闭 HTTP 服务 → 关闭 GUI 与托盘 → 释放互斥体 → 刷新日志。

`HTTPServer.shutdown()` 应由 `serve_forever()` 所在线程之外调用；若服务循环未启动或已退出，应按控制对象状态处理，避免关闭过程死锁。常规退出不使用 `os._exit(0)` 跳过清理。

## 9. 构建流程优化

### 9.1 保持 onedir，使用隔离的构建环境

先保留 `onedir + Portable ZIP + Inno Setup`。本次问题不需要通过迁移 onefile 或更换打包器解决。

- 依赖检查与依赖安装分开；正式构建只消费已经验证的固定环境。
- 用 `sys.executable -m PyInstaller` 调用打包器，防止 PATH 指向另一套解释器。
- 开始时校验解释器版本、x64 架构和关键依赖；不满足则停止。
- 记录 PyInstaller 警告并按实际可达功能分类，不能把所有 missing module 都当成故障，也不能全部忽略。
- 不全局设置 `NO_PROXY=*`；只对本地回环请求绕过代理，构建下载遵循明确配置。
- 不按 EXE 文件名强制结束用户所有实例；仅处理本轮构建可确认归属的资源。

### 9.2 在 staging 中完成混淆和打包

当前 PyArmor 流程会备份、删除并替换开发源码，存在中途失败导致恢复条件未满足的风险。建议改为：

```text
源代码快照 → 独立 staging → 在 staging 混淆
          → PyInstaller 构建 → 产物检查 → 冒烟测试 → 归档
```

源码目录始终只读。staging 使用唯一目录；清理前校验绝对路径属于本项目构建根目录。清理失败、混淆失败、关键文件缺失时停止正式发布，不静默切换成另一种保护策略。

PyArmor runtime 包名应从实际输出获取，不固定写死 `pyarmor_runtime_000000`。更换解释器或 PyArmor 版本后必须重新验收；本方案当前不要求更换它们。

### 9.3 DLL 与模型收集

- 使用与锁定版本匹配的官方 PyInstaller hook，并验证最终产物内容。
- 仅补充 hook 未覆盖的必要文件，不默认多路径复制就是可靠。
- 原生二进制通过合适的 binaries / hook 机制收集，保证其依赖得到分析。
- 移除或收紧“缺少 ARM64 / x86 时回退 x64”的宽泛补丁；架构不匹配应明确失败。
- `common_old.onnx` 与已检查的 ddddocr 1.5.6 默认路径一致；在固定版本下保留按需收集，并验证真实识别。
- cv2 mock 只适用于已验证的分类路径；若新增滑块、检测等功能，应重新评估真实 OpenCV 需求。
- 不能把返回占位验证码视为 OCR 加载成功，发布自检必须识别缺失模型和推理 DLL。
- 对 UPX 开启与关闭分别测量体积、启动耗时和兼容性；没有证据前不把压缩收益置于稳定性之上，也不预先认定它就是现有故障根因。

### 9.4 发布文件清单与版本来源

由单一版本来源生成构建版本、安装器版本、EXE 元信息、ZIP 文件名和更新说明。建议每次构建同时生成：

| 文件 | 内容 |
| --- | --- |
| `build-info.json` | 版本、提交标识、解释器和工具版本、架构、构建时间、混淆状态、验证范围 |
| 文件清单 | 发布目录内各文件相对路径、大小与哈希 |
| `SHA256SUMS.txt` | 本次明确生成的 ZIP / Setup 校验和，不自动混入所有历史产物 |
| 使用说明与更新说明 | 当前真实启动方式、应用内修复流程、主动应急访问说明、退出方法和诊断入口 |

从全新 staging 生成归档，不直接重压已经运行过的目录。归档前拒绝真实配置、会话文件、授权、日志、抓包和私钥；公开 CA 证书如 `certifi/cacert.pem` 不能仅因 `.pem` 后缀被误判为私钥。

现有发布目录出现用户运行文件，不等于已发布 ZIP 含有这些文件；二者分别检查，不能据目录状态直接宣称凭据已经泄露。

## 10. 安装版、便携版与数据目录

### 10.1 ZIP、主程序 EXE 与安装版 EXE 的区别

| 名称 | 是什么 | 用户如何使用 | 是否可以单独拿走 |
| --- | --- | --- | --- |
| `XMU_Gym_Booking_vX.Y.Z_Portable_Windows_x64.zip` | 完整应用目录的压缩包，含主程序、`_internal`、模型、模板及组件修复资源 | 完整解压到可写目录，再双击目录内主程序 | 分发整个 ZIP；不能只发包内 EXE |
| ZIP 内的 `XMU_Gym_Booking.exe` | PyInstaller onedir 的主启动程序，依赖同目录资源 | 直接运行，不经过应用安装向导 | 不能脱离 `_internal` 等依赖目录单独运行 |
| `XMU_Gym_Booking_Setup_vX.Y.Z.exe` | Inno Setup 安装器，将同一应用构建安装到用户目录并建立快捷方式 | 双击安装后，从桌面或开始菜单启动 | 安装器本身可单独下载，但它不是主程序 EXE |

当前采用 onedir，不计划另做“把所有依赖塞进一个主程序”的 onefile 版本。ZIP 和 Setup 只是同一应用的两种交付形式，不应产生功能差异；Setup 也不会仅因为扩展名是 `.exe` 就自动解决 Runtime 缺失，仍要实现组件检测和安装逻辑。

安装器中的桌面快捷方式、主开始菜单项及安装后启动统一进入应用模式，不再默认传入 `web`。应急浏览器通过用户主动选择或明确 CLI 命令进入。

### 10.2 Release 双制品发布计划

同一个 Release 同时提供以下文件，版本号从同一来源生成：

```text
XMU_Gym_Booking_vX.Y.Z_Portable_Windows_x64.zip
XMU_Gym_Booking_Setup_vX.Y.Z.exe
SHA256SUMS.txt
release-notes.md
```

- ZIP 面向希望完整解压后直接运行、不安装应用本体的用户；明确提示需要完整解压，不能在压缩包预览中运行或只复制 EXE。
- Setup 面向希望自动安装、建立快捷方式并完成组件检查的用户。
- 两种制品都包含官方轻量 Bootstrapper 及联网说明，已有 Runtime 时不重复安装；均以应用内界面作为验收标准。
- 使用同一份通过检查的应用 staging，分别生成 ZIP 和 Setup；对资源和版本进行一致性校验。
- 当前脚本在本地没有 Inno Setup 时会跳过 Setup。正式双制品发布应将这种情况视为发布门禁未满足，补齐编译环境后再发布，不能宣称两种制品都已生成。
- 本次只修改发布计划，不实际构建、上传 Release、安装 Runtime 或提交代码。

### 10.3 资源目录与可写目录分离

| 数据 | 安装版建议 | 便携版建议 |
| --- | --- | --- |
| EXE、DLL、模型、模板 | 安装资源目录 | 解压资源目录 |
| 配置、登录态、授权、防回拨状态 | 用户数据目录，迁移时保持原有授权语义 | 明确便携标记后存同目录；不可写时提示或提供迁移选择 |
| 日志、WebView2 用户缓存 | 用户可写目录 | 可写的便携数据目录或明确的用户目录回退 |
| 临时文件 | 受控临时目录，退出时清理适当内容 | 同左 |

安装版可使用 `%LOCALAPPDATA%\XMU_Gym_Booking` 作为数据根目录。便携模式应由明确标记或构建配置决定，不能仅通过目录是否可写来猜测。

配置、授权查找和防回拨数据必须一起设计迁移：先备份、校验、再切换，防止已有用户升级后丢失登录或授权。原始数据保留到迁移成功，不在升级或卸载中默认删除用户数据。

资源路径以应用资源根目录解析，包括 PyInstaller 的 `_MEIPASS`；用户数据路径由统一目录模块给出。不能只依赖全局 `os.chdir()` 来解决所有路径问题。

### 10.4 说明文档与实际产物一致

当前旧指南提到的快捷 BAT、使用说明复制过程以及 `.github/workflows/release.yml`，需按实际检出和产物核对。尚未实现的 CI 不应写成现成能力。

## 12. 验证计划

### 12.1 自动化回归

1. 给 `socket.getfqdn` 注入 `UnicodeDecodeError`，确认两种本地服务器都不调用它；发送实际 HTTP 请求并检查响应。
2. 分别模拟端口占用、权限不足、地址不可用，验证分类、退出码和资源回收。
3. 模拟启动延迟、线程异常和健康响应标识不匹配，确保界面只在正确实例就绪后打开。
4. 验证健康接口不调用学校 API、登录监控、OCR 或硬件指纹查询。
5. 验证自定义端口及自动分配端口传递到窗口、浏览器和托盘。
6. 模拟 pywebview 导入失败、Runtime 未检测到、异步初始化失败、页面超时，验证默认进入原生修复窗口，且没有自动浏览器调用。
7. 验证安装器取消、安装失败、安装后仍不可用、受控重启与重试次数限制；原生修复窗口不依赖 WebView2 或 .NET 成功加载。
8. 验证仅主动选择应急方式时打开浏览器，并覆盖浏览器打开失败、控制入口创建失败、重复启动和退出的边界行为。
9. 验证程序目录不可写、旧数据迁移失败、配置与授权保留。
10. 验证 staging 构建失败不改变源代码，关键文件缺失或敏感文件混入会阻止归档；缺少 Setup 编译器时阻止双制品发布。
11. 在最终产物中执行真实 OCR 推理、模型缺失检查及授权模块加载检查；不能只验证 mock 返回值。

现有 `tests/test_single_instance.py` 中“任意 `OSError` 均静默返回”的预期应随方案调整，避免旧测试把错误行为固定下来。

### 12.2 Windows EXE 验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 中文电脑名、中文 Windows 用户名 | 不出现 FQDN 解码导致的服务退出 |
| 中文、空格、较深解压路径 | 模板、模型、DLL、配置和日志路径正确；记录实际支持的路径范围 |
| 无 Python、无开发环境 | EXE 正常运行，依赖自包含 |
| 无 WebView2 Runtime | 显示原生修复窗口；确认安装成功后在应用内打开，不自动启动浏览器 |
| 有 Runtime 且注册正常 | 独立桌面模式可用 |
| 有组件文件但注册缺失或损坏 | 不凭目录误判；提供修复与重试，应用内可用前不宣告成功 |
| WebView2 异步初始化失败 | 准确分类并进入修复窗口，不无限空白、不自动打开浏览器 |
| 用户取消组件安装、安装失败或被策略阻止 | 保留原生窗口，提供重试、退出及主动应急入口，无安装重启循环 |
| 8080 被其他程序占用 | 不打开其他程序页面；自动模式换端口或明确失败 |
| CLI 显式端口被占用 | 提示准确，非零退出码 |
| 冷启动慢、CPU 或磁盘繁忙 | 就绪前不打开错误页面；超时有诊断信息 |
| 程序目录只读、普通用户 | 使用可写目录或清楚提示，不无声失败 |
| 默认浏览器关联失效 | 默认应用模式不受影响；仅在主动应急访问时提供复制地址与重试 |
| 多次双击、窗口在托盘 | 唤起已有实例或准确报告启动中，无重复控制中心 |
| 关闭浏览器后重新打开 | 已开启任务继续运行，控制台可以重开 |
| 托盘创建失败 | 保持可见控制入口，不把窗口隐藏丢失 |
| 明确退出后再次启动 | 端口和句柄释放，任务无残留实例 |
| ZIP 完整解压后首次运行 | 无 Runtime 时可使用附带资源修复，随后在应用内打开；不要求手输地址 |
| Setup 安装、升级、卸载 | 完成组件检查，快捷方式进入应用模式；旧配置和授权不丢失 |
| 校园网受限、断网启动 | 本地服务与提示可用，外部请求失败不伪装成启动失败 |

优先支持和声明已测试的 Windows x64 平台。若没有验证 ARM64、32 位或旧 Windows，不把 DLL 路径回退等同于正式支持。

### 12.3 发布门禁与回滚

- 最终 ZIP 解压后测试，Setup 在独立的干净系统快照安装后测试；两者均需覆盖无 Runtime 情况，不能让前一个测试安装的 Runtime 掩盖后一个制品的问题。
- ZIP 和 Setup 从同一应用构建生成，版本及关键资源一致；Release 同时提供两者，不将包内主程序 EXE 当作第三个独立制品上传。
- 冒烟测试通过前不发布；哈希只证明文件一致，不证明功能正确。
- 留存上一稳定版、构建信息和本轮依赖集合，确保可以重建或回滚。
- 数据格式变动保持向后兼容；回滚不得重置登录和授权数据。
- 更新说明写明已验证范围和仍需用户反馈的边界，不使用“100% 兼容”等承诺。

## 13. 交付范围与结论

第一阶段应优先完成：本地服务器绕开主机名解析、启动握手和异常回传、WebView2 检测及原生安装修复流程、可见控制与退出管理。随后完成数据目录、构建隔离和 ZIP / Setup 双制品发布门禁。

保留 Python 3.8，通过运行层解决已定位的中文主机名触发链。默认在应用内打开预约界面；缺少 WebView2 时先提供安装修复，浏览器仅保留为主动选择的应急入口，手动输入 `127.0.0.1` 不属于正常使用流程。Release 同时提供完整便携 ZIP 和安装版 Setup.exe，二者功能相同、启动目标一致。
