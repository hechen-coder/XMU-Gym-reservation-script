# 微信 ClawBot 通知迁移说明

## 结论与范围

可行。参考目录 `D:\Downloads\XMU-Rollcall-Bot-Integrated-main\XMU-Rollcall-Bot-Integrated-main\xmu-rollcall-cli` 中，`xmu_rollcall/wechat_notifier.py` 已实现扫码登录、接收一条消息绑定目标、恢复 context_token 并发送文本。其通知工厂只选择单一 provider，且 SDK 要求 Python >= 3.9；本项目发布基线为 Python 3.8，因此直接复用该工厂或强制安装 SDK 都不合适。

本分支独立实现所需的同步 HTTP 文本接口，沿用参考项目的凭据/上下文持久化流程；不复制参考项目代码，不读取或迁移真实账号凭据。现有 SMTP 通道保留，微信通过 `notify.wechat.enabled` 独立加入分发，二者并发执行。

## 依据

- [参考 SDK 的 Python 文档](https://www.wechatbot.dev/zh/python)：Python >= 3.9；发送主动消息前需要已有会话上下文。
- [腾讯登录实现](https://github.com/Tencent/openclaw-weixin/blob/main/src/auth/login-qr.ts)：POST 获取二维码、扫码确认、配对码、IDC 重定向、本地 token 复用。
- [腾讯 API 实现](https://github.com/Tencent/openclaw-weixin/blob/main/src/api/api.ts) 与 [消息构造](https://github.com/Tencent/openclaw-weixin/blob/main/src/messaging/send.ts)：请求头、base_info、sendmessage 字段、业务错误处理。
- [SDK 协议说明](https://www.wechatbot.dev/en/protocol)：保存最近入站消息的 context_token；-14 表示会话过期。

协议标识按核查时腾讯包版本 2.4.10 固定，不在运行时联网下载或自动升级。后续协议变化需回归验证。

## 接入与使用

1. `python -m pip install -r requirements.txt`，运行 `python main.py web`。
2. 打开“通知提醒”。邮箱填入地址即接收邮件，留空即停用邮件。
3. 微信勾选独立开关，点击“扫码连接”；扫描手机微信二维码并确认，按需填写手机显示的配对码。
4. **用扫码账号向 bot 发一条消息**，完成绑定；测试结果分别展示邮箱和微信状态。
5. 开启通知总开关并保存。新设置对新建通知实例生效，已有定时/余量监测任务需停止后重新启动。

仅登录不代表已绑定；本地保存的绑定也不代表手机已收到消息。测试结果“已提交”表示服务端未报告业务错误，真实收件和锁屏提醒需在手机端确认。

配置示例：

```yaml
notify:
  enabled: true
  channel: email
  email:
    to_addrs: ["your_email@qq.com"]
  wechat:
    enabled: true
    cred_path: wechatbot-credentials.json
    state_path: wechat_state.json
    send_timeout: 15
    use_env_proxy: false
```

路径相对 `config.yaml` 所在目录解析，支持现有 SDK 的 token/baseUrl/userId 凭据字段。默认凭据和上下文文件已忽略，不经 Web API 回传；自定义文件名也应保持本地，不提交 Git。文件采用原子替换并设置当前系统支持的权限；Windows 的 chmod 不提供完整 ACL 隔离能力。

## 实现边界

- `notify/wechat.py`：Python 3.8 同步协议、超时、业务错误校验、过期清理、原子存储和脱敏日志；凭据只发送到 HTTPS 的微信 API 域名，不跟随 HTTP 重定向。
- `notify/wechat_binding.py`：后台扫码与配对码流程；绑定只接受扫码用户；监听消息仅刷新该用户上下文，不把其他发件人切换为通知目标。
- `Notifier`：邮箱与微信并发；某端异常仍返回另一端结果；总开关关闭则全部不发。
- Web：独立微信开关、二维码/配对码、连接状态、恢复/断开、分通道测试反馈；测试使用表单当前值，保存由独立按钮执行。
- 消息：成功提醒保留场馆、日期、时段和核对提示；测试提醒为一句话；失败通知保留故障原因与计划上下文。
- 打包：增加 Python 3.8 兼容的 qrcode 依赖、约束和 PyInstaller 隐式导入；未在本次生成或发布 EXE。

程序启动后，已启用的微信监听会恢复会话、刷新上下文。断开时会删除本地凭据和绑定，旧长轮询结束可能需要约 40 秒；此时新连接会明确提示等待。退出程序也会停止监听。CLI 单次通知读取最近保存的上下文；首次绑定通过网页完成。

## 风险与待验证

微信登录或上下文可能过期。登录过期需重新扫码，上下文不可用时需向 bot 发新消息并测试。QQ 邮箱辅助提醒与 ClawBot 是独立功能，不承诺开启邮箱就会触发微信提示。一个 bot 账号应由一个客户端轮询，避免与参考项目同时运行同一 bot 导致游标竞争。

自动化测试使用模拟 HTTP 返回，浏览器验证使用隔离配置与无预约数据；未使用个人账号执行扫码和真实微信/邮件投递，也未验证打包后的可执行文件。真实手机端收件是剩余验收步骤。

## 2026-10-22 本机连接失败排查与修复

用户日志仅显示 `微信连接失败 (WeChatError)`，此前日志隐藏了具体失败原因。实际失败位于匿名 `get_bot_qrcode` 请求，尚未进入扫码或会话绑定。

在用户当前 Python 3.8.8 / requests 2.25.1 / urllib3 1.26.4 环境中，默认系统代理路径复现 `ValueError: check_hostname requires server_hostname`。堆栈经过 `urllib3.connectionpool._prepare_proxy` → `urllib3.connection._connect_tls_proxy` → Python SSL，说明失败发生在 HTTPS 代理的 TLS 初始化。对同一微信接口执行直连，得到 HTTP 200、ret=0，且包含二维码字段。

修复仅限微信客户端：默认传入空的 http/https/all 代理路由，覆盖 Windows/环境变量的代理继承；TLS 证书验证仍然开启，其他请求客户端的代理设置不变。确需代理时，可在 `notify.wechat.use_env_proxy: true` 显式启用，需确保当前代理和 Python TLS 环境匹配。未更改系统代理、全局 requests 或 Python 包版本。

日志和界面现在包含失败接口与脱敏原因，区分代理错误、TLS 错误、超时、HTTP 状态、非 JSON 返回与业务返回码，不输出服务端任意文本、二维码查询参数或令牌。

验证：修复后的正式 `WeChatClient` 在当前机器真实请求二维码成功；新增代理继承隔离、代理选项、旧 TLS 异常诊断、HTTP/JSON 诊断和日志脱敏用例，完整回归 284 项通过。真实扫码确认与手机端收件仍由用户完成。

本地运行验证：确认定时预约、余量监测均未启动后，重启原 `main.py web` 服务以加载修复。真实请求 `/api/notify/wechat/login` 返回 success=true，随后 `/api/notify/wechat/status` 返回 phase=wait、二维码 PNG 已生成、logged_in=false、bound=false，证明已进入等待手机扫码阶段；未代替用户确认登录或发送通知。网络仍可能瞬时超时，此时会显示具体接口和超时原因，可重试。
